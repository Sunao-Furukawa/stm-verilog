# STM-RTOS

[English](README.md) | **日本語**

STM-1.2 用の小さなリアルタイム OS です。`tools/asm.py` でアセンブルする 1 本のアセンブリ
ソース [`rtos.s`](rtos.s) に、カーネルとデモ用の 4 タスク、結果の自己検査が入っています。
同じカーネルで Arty A7-35 のスイッチと UART を使うアプリケーションの例が
[`greet_uart.s`](greet_uart.s) です ([後述](#アプリケーションの例-スイッチであいさつを切り替える-greet_uarts))。

## 特徴

* **4 タスク, 固定優先度のプリエンプティブ・スケジューリング** (数字が小さいほど優先度が高い)。
  優先度の高いタスクが待ちから戻ると、その場で切り替わります。同じ優先度のタスクは
  `YIELD` で順番に回ります。
* **タスクはユーザモード** で動き、カーネルとは **システムコール** でやりとりします。
* **計数セマフォ** 4 個, **メールボックス** 2 個 (各 4 通までたまる)。受信待ちのタスクが
  いれば、送信したメッセージはそのタスクに直接渡します。
* タスクが **例外** (オーバフロー, 違法命令, コンペアストップ, AXI4 版のバスエラー) を
  起こしたら、そのタスクだけを終了させてログに記録します。
* 全タスクが終わると、アプリケーション側の終了処理 (`APP_DONE`) を呼びます。
  待ちのタスクだけが残ったら `DEADLOCK` (0x3E0) で止まります。

STM には **タイマ割り込みも外部割り込みもありません** (割り込みは違法命令・コンペアストップ・
オーバフロー・AXI4 版のバスエラーの 4 種類だけ)。そのため時間による切り替え (タイムスライス,
`sleep`) はできず、タスクの切り替えはシステムコールのときだけ起きます。

## システムコール

タスクは `SVC n` で呼びます。`SVC` は `tools/asm.py` に追加した命令で、未定義命令
`E00000nn` になります。実行すると違法命令例外 (INTTYPE=1) でカーネルに入るので、
カーネルは XPC が指す命令語の上位 8 ビットが `E0` ならシステムコール、それ以外なら
本当の違法命令とみなします。

引数は GR1, GR2、戻り値は GR1 です。それ以外の GR はすべて保存されます。

| 番号 | 名前 | 引数 | 戻り値 |
|---|---|---|---|
| 0 | EXIT | | (戻らない) |
| 1 | YIELD | | |
| 2 | SEM_WAIT | GR1 = セマフォ (0〜3) | 0 / -1 (ID 不正) |
| 3 | SEM_SIGNAL | GR1 = セマフォ | 0 / -1 |
| 4 | SEND | GR1 = メールボックス (0〜1), GR2 = メッセージ | 0 / -1 (ID 不正, 満杯) |
| 5 | RECV | GR1 = メールボックス | メッセージ / -1 |
| 6 | LOG | GR1 = 値 | (ログ領域 0xE00 に追加) |
| 7 | GETTID | | タスク番号 (0〜3) |

`SEM_WAIT` は計数値が 0 なら、`RECV` は箱が空なら待ちに入ります。

## しくみ

```
 タスク (ユーザモード)          カーネル (カーネルモード)
   SVC n  ──違法命令例外──▶  TRAP (TBR=0x440)
                               GR0-15, XPC, XPSW を TCB に保存 (SVR0 = 実行中の TCB)
                               INTTYPE と命令語を見て分岐表 0x400+4n へ
                               ...処理...
                               SCHED: 実行可能で最も優先度の高いタスクを選ぶ
   ◀──────── RFE ───────────  DISPATCH: TCB から GR, XPC, XPSW を戻す
```

* **TCB** (0x60 バイト): GR0〜15, PC, PSW, 状態 (休止 / 実行可能 / 待ち), 優先度,
  待っているオブジェクトの番地, タスク番号。
* **保存**: アーキテクチャ文書 (`doc/japanese/arch-details01`) に書かれている方法そのままで、
  `WSR 9,15` で GR15 を SVR1 に逃がし、`RSR 15,8` で SVR0 (= 実行中の TCB) を GR15 に
  取り出してから GR を順に書きます。こうすると、タスクは 16 本の GR をすべて使えます。
* **待ち行列は持たず**、起こすときは TCB を 4 個調べて、そのオブジェクトを待っている
  タスクのうち優先度の最も高いもの (同じなら番号の小さいもの) を選びます。
* タスクはユーザモード (PSW の USER=1) なので、特権命令 (RSR/WSR/RFE) を実行すると
  違法命令例外になり、終了させられます。

### メモリマップ (4KB)

| 番地 | 内容 |
|---|---|
| 0x300 | リセット (`main`)。0x3D0 `DEAD`, 0x3E0 `DEADLOCK`, 0x3F0 `SUCCESS` |
| 0x400〜 | システムコールの分岐表 (8 語) |
| 0x440〜 | トラップ入口とカーネル |
| 0x900〜 | ユーザタスク (T0 0x900, T1 0x980, T2 0xA00, T3 0xA80) |
| 0xB00〜 | 全タスク終了後の処理 (ログの検査) |
| 0xC00〜0xD7F | TCB × 4 |
| 0xD80〜0xE7F | カーネル変数, セマフォ, メールボックス, ログ (起動時に 0 にする) |
| 0xF00〜 | タスク表 (入口番地, 優先度) |
| 0xF40〜 | ログの期待値 |

## デモ (自己検査)

4 つのタスクが次のように動き、各タスクが `LOG` で残した値の列を最後に期待値と比べます。
一致すれば `SUCCESS` (0x3F0) で止まります。

| タスク | 優先度 | 動作 |
|---|---|---|
| T0 | 1 | メールボックス 0 から 3 通受け取る (毎回待ちに入る)。セマフォ 0 を上げる |
| T1 | 2 | 0x11, 0x22, 0x33 を送る (送るたびに優先度の高い T0 に切り替わる)。続けて 0x44, 0x55 を送る (受け手がいないので箱にたまる) |
| T2 | 3 | T3 と `YIELD` で交互に動く。セマフォ 1 を上げて T3 を起こす。最後にわざとオーバフローを起こし、カーネルに終了させられる |
| T3 | 3 | セマフォ 1 を待つ。箱にたまった 2 通を受け取る。不正な ID で -1 が返ることを確かめる |

ログの期待値 (19 語):

```
A0 B0 11 B1 22 B2 33 B3 B4 C0 D0 C1 C2 C3 D1 44 55 C4 E4
```

最後の `E4` は T2 のオーバフロー例外 (`E0` + INTTYPE 4) をカーネルが記録したものです。
T0, T1 はシステムコールをまたいで GR10 が保存されていることも確かめています。

## 動かし方

`verilog` フォルダで:

```sh
python tools/asm.py rtos/rtos.s 20000 -o work/rtos.dat
python tools/mem2hex.py work/rtos.dat work/rtos.hex
# stm_sys (理想メモリ): 約 7,500 サイクル
iverilog -g2001 -I rtl -o work/sim.vvp tb/tb_stm.v rtl/stm_sys.v rtl/stm_cntl.v rtl/stm_exu.v rtl/stm_regfile.v rtl/stm_memory.v
vvp work/sim.vvp +HEX=work/rtos.hex +PC=300 +CYCLES=20000
# AXI4 版 (命令キャッシュ 4KB, 乱数ウェイト): 約 28,000 サイクル
iverilog -g2001 -I rtl -o work/axi.vvp tb/tb_stm_axi.v tb/axi4_mem_slave.v rtl/stm_axi_top.v rtl/stm_icache.v rtl/stm_axi_master.v rtl/stm_cntl.v rtl/stm_exu.v rtl/stm_regfile.v
vvp work/axi.vvp +HEX=work/rtos.hex +PC=300 +CYCLES=400000 +RANDOM +SEED=1
```

`RESULT: stop at PC=000003f0 ... -> OK` と出れば成功です。`run_bup_axi.sh` / `run_bup_axi.ps1`
は bup などと一緒にこの RTOS も 5 通りの構成で実行します。

### 検証

* `stm_sys` (キャッシュミス無し): 成功 (7,518 サイクル)。
* AXI4 版: ウェイト無し + 乱数ウェイト・応答順入れ替えの種 20 通り × 4 構成
  (4KB キャッシュ, 同 + `BYTE_SWAP=1`, 16 バイト × 2 ラインのキャッシュ, キャッシュ無し) の
  81/81 が成功。
* `stm_sys` の `+RANDOM` (C 版 `stmsiml -r` 相当の乱数キャッシュミス): 20 通りすべて成功。
  以前は 20 通り中 1 通り (`SEED=7`) が `DEADLOCK` で止まり、元の設計のフェッチの不具合
  ([../README.ja.md](../README.ja.md) 8 章の「未解決 BC を発行したら古いフェッチを取り消す」) と
  考えていました。しかし下の不具合 3 の対策 (RFE の後ろに条件分岐を置かない) を入れると止まらなく
  なりました。対策前のカーネルでは、この実行で RFE の直後に `G_BC_PENDING` が 1 のまま残ることが
  26 回あったので、不具合 3 が原因だったと考えられます。

## アプリケーションの例: スイッチであいさつを切り替える (`greet_uart.s`)

[`greet_uart.s`](greet_uart.s) は、この RTOS の上で動く実機 (Digilent Arty A7-35) 用のプログラム
です。スライドスイッチ SW1, SW0 で選んだあいさつを、約 0.5 秒ごとに UART (115200 baud) に出します。
カーネル部分は `rtos.s` と同じで、ユーザタスクとデータだけが違います。

| SW1 | SW0 | 出力 |
|---|---|---|
| 0 | 0 | `Hello` |
| 0 | 1 | `Nihao` |
| 1 | 0 | `Konnichiwa` |
| 1 | 1 | `annyeonghaseyo` |

| タスク | 優先度 | 動作 |
|---|---|---|
| T0 | 1 | 出力タスク。メールボックス 0 から文字列の番地を受け取り (`RECV`)、UART に 1 文字ずつ出す |
| T1 | 2 | スイッチのタスク。GPIO からスイッチを読み、文字列の番地をメールボックス 0 に送る (`SEND`)。受信待ちの T0 の方が優先度が高いので、その場で T0 に切り替わり、1 行出し終わってから T1 に戻る。その後、空ループで約 0.5 秒待つ |
| T2, T3 | 3 | 使わない (すぐ `EXIT`) |

タイマ割り込みが無いので、待ち時間は T1 の空ループで作ります。1 回 3 サイクルなので、
`DELAY` (0xF30) の 4,000,000 回で 24 MHz なら 0.5 秒です。UART Lite (`F000_0000`) と GPIO
(`F001_0000`) は CPU の I/O 領域にあり、ユーザモードのタスクからそのまま読み書きします。

`verilog` フォルダで:

```sh
python tools/asm.py rtos/greet_uart.s 20000 -o work/greet_uart.dat
python tools/mem2hex.py work/greet_uart.dat work/greet_uart.hex
python rtos/check_bc.py rtos/greet_uart.s      # conflicts: 0 なら OK
cd syn/vivado
vivado -mode batch -source create_bd.tcl -tclargs xc7a35ticsg324-1L ../../work/greet_uart.hex arty_a7_35.xdc
```

ブロックデザインとピン配置は [../syn/README.ja.md](../syn/README.ja.md) の最後の節を参照してください。

## ハードウェアの不具合と、その対策

RTOS を作る中で、CPU 本体の不具合を 3 つ見つけました。どれも元の CHDL の論理をそのまま
変換した部分にあり、元の STM-1.2 の設計の不具合です。
回帰テスト (bup) には該当するパターンが無いため、これまで表に出ていませんでした。
CPU 本体は C 版とのサイクル一致を保つため変更せず、RTOS 側で避けています。
[`check_bc.py`](check_bc.py) がソースを静的に検査します。

```sh
python rtos/check_bc.py rtos/rtos.s      # conflicts: 0 なら OK
```

### 1. 予測ミスで取り消した命令の結果がバイパスされる

条件分岐の CC がまだ出ていないと、STM は静的予測 (後方分岐は taken, 前方分岐は not taken)
で先の命令を発行します。予測が外れたサイクルに、正しい側の最初の命令組 (最大 2 命令) が
D サイクルで発行されますが、このとき A サイクルにいる **取り消し中の命令の結果がバイパス
されてしまいます**。D → A のオペランドのバイパス (140_d_dat.vh) が、書き込みフラグ
(`A_WE2` など) だけを見ていて、取り消し (`A_V_NOCAN`) を見ていないためです。

実際に起きた例:

```
K_SEND:  L   1,13(4)
         CU  1,%2
         BGE K_ERR        # K_ERR は後方なので taken と予測 → K_ERR の O 1,0,%-1 が先に発行される
         SL  1,1,%5       # 予測ミス後, この SL が GR1 = -1 (取り消された O の結果) を受け取った
         ...
K_ERR:   O   1,0,%-1
```

対策 (`check_bc.py` が検査):

* エラー処理などへの分岐は **前方分岐** にする (予測で先に進まない)。
* 分岐の両側で, 予測した側の最初の 4 命令が書くレジスタを, 反対側の最初の 2 命令が読まない。
  (取り消し時に A にいるのは 1 組 = 2 命令ですが、余裕を見ています。)

### 2. WSR の GR, ストアのベースレジスタはロードの結果を待たない

A サイクルで「オペランドがまだ届いていない」ことを見るインタロック (`A_EAB`, 060_g_srq.vh) は
GR を書く命令 (`A_WE1`, `A_WE2`) か CC を変える命令しか対象にしていません。そのため
GR を書かない WSR、ストア, J は、直前のロードの結果を待たずに古いレジスタ値を使います。

```
L   1,15(40)
WSR 5,1          # XPC にロード前の GR1 が入ってしまう
```

対策: ロードした値は、GR を書く EX 命令 (`O 1,1,%0` など) でコピーしてから使う
(EX 命令はインタロックするので、その結果は正しくバイパスされる)。

### 3. RFE の後ろで発行された条件分岐が「未解決」のまま残る

RFE が W サイクルに着くと、パイプラインの命令はすべて取り消されます (`CANCEL_BY_INT` =
割り込み | RFE | 状態変更, 050_op_lb1.vh)。ところが未解決の条件分岐があることを示す
`G_BC_PENDING` (210_g_bc.vh) を 0 に戻すのは割り込み (`WW_INTERRUPTION`) だけで、RFE では
戻しません。そのため、RFE の後ろに置いた条件分岐が先に D で発行されると、その分岐は取り消された
のに「未解決」の印だけが残ります。

* 復帰先のタスクで CC を作る最初の命令が、この分岐を「解決」します。結果が予測と違えば、
  復帰先の命令が取り消され、その条件分岐の飛び先 (カーネルの中) へ進んでしまいます。
* AXI4 版の I/O 領域へのロードは、未解決の条件分岐があると A サイクルで待ちます。その後ろの
  命令は進めないので分岐は解決されず、そこで止まってしまいます。

実際に起きた例 ([`greet_uart.s`](greet_uart.s) を作っていたとき):

```
DISPATCH: ...
         RFE
K_LOGPUT: L   2,LOGCNT
         C   2,%20
         BGE KLP_RET     # RFE の後ろで発行され, G_BC_PENDING = 1 のまま残った
...
TASK1:   SETHI 9,%-FFF
         L   3,9(0)      # スイッチ (I/O 領域) のロードがここで止まり続けた
```

対策 (`check_bc.py` が検査): RFE の後ろには条件分岐を置かない。カーネルでは RFE の直後に
自分自身への無条件分岐 (`DSP_SPIN: B DSP_SPIN`, 実行はされない) を置いています。
`check_bc.py` は、RFE の後ろ 8 命令 (無条件分岐はたどる) に条件分岐が無いことを調べます。

## アセンブラ (`tools/asm.py`) の変更

* **`SVC n`** 命令を追加 (`E00000nn`, n は 16 進 0〜FF)。
* 元の `asm.pl` は 1 パス目 (ラベルの番地を決める) で `SETHI`, `RSR`, `WSR`, `RFE` を
  数えていなかったため、これらの後ろ (次の `EQU` まで) のラベルの番地がずれていました。
  これを直しました。bup0/bup1/samples/tests/bench の既存 74 ファイルでは出力は 1 文字も
  変わらないことを確認しています (いずれも、これらの命令の後には `EQU` を置いていた)。

asm.py の書き方の注意 (元の asm.pl と同じ):

* 命令は行頭から書く (1 パス目は行頭で命令を見分ける)。ラベルは 1 行に 1 つだけ書く。
* データ行の後ろで分岐命令を書くときは、間に `EQU` を置く (2 パス目はデータ行で番地を
  0 に戻してしまう)。データ行の後ろにコメントを書かない。
* ラベル名に `RFE` を含めない。`J` の飛び先のラベル名を `B` で終わらせない
  (どちらも別の命令と誤認される)。
